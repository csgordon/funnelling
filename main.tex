\section{Introduction}
Java includes a useful feature called \emph{method-local inner classes}, which is surprisingly subtle.
Like anonymous inner classes, this is a way for a method in a Java program to declare a class whose details are defined
locally, entirely within the method, when the identity of the class is not needed outside the method's scope.
However, these local classes are named, which allows them to be used with other language features exploiting nominal types.
For example, one can cast objects to the method-local class type.

Unfortunately, as Servetto et al.~\cite{unsound_presentation} pointed out, these features interact unsoundly with Java generics.
In generic methods (or methods of generic classes), a method-local inner class \lstinline|MyFoo| 
which extends a type that depends on generic parameters is treated the same regardless of whether it was allocated with the same
generic parameters, or different generic parameters. Servetto et al. probed the behaviour of JVM languages which
supported the same feature (Scala and Kotlin) and found that these had the same unsoundness problem for some use cases,
but did flag concerns in other cases. However this was not systematically investigated.

In this paper we clearly articulate the problem they observed, characterize the key properties that lead to the issue, and demonstrate
both dynamic and static approaches to resolve the issue in future languages. 
The dynamic approach is a specific interpretation of type tests with reified generics, providing guidance to language implementors on a subtle design choice available in that space.
\mjnote{modern Java accepts \texttt{instanceof C<Ts>} only when the static type determines \texttt{Ts}; with that rule an erased and a reified runtime give the same answer on every well-typed program. The dynamic approach then only concerns languages without that rule (C\#-like). Funnelling could be presented as the solution, with reification as a side remark.}
The static approach is a general solution for tracking when a nominal object type \emph{declaration} effectively captures generic parameter instantiations from its dynamic context.

\begin{lstlisting}[numbers=left]
public class Broken {
  static <X> Foo<X> m(Object other, final X x){
    class MyFoo extends Foo<X>{ public X x(){ return x; } } (*\label{line:MyFoo}*)

  }
  public static void main(String[] a) {

    Foo<String> r2= Broken.<String>m(r1,"Hi"); (*\label{line:strcall}*)
    System.out.println(r1.x()); //5
    System.out.println(r2.x()); //Throws ClassCastException: ..
  }
}
class Foo<X>{ public X x() {return x();} }
\end{lstlisting}
\caption{Subtly broken Java code}
\label{fig:original_example}
\end{figure}

Figure \ref{fig:original_example} demonstrates the issue. Line \ref{line:MyFoo} declares a method-local inner class
\lstinline|MyFoo|, which depends on the generic parameter instantiation for \lstinline|X| when the method is invoked.
The \lstinline|main| method invokes \lstinline|m| twice. Line \ref{line:intcall} invokes it for \lstinline|Integer|s.
Since the \lstinline|other| argument for that call is not a \lstinline|MyFoo|, the first invocation returns
a \lstinline|MyFoo| which is a \lstinline|Foo<Integer>|.
This result is then passed back in to the second call to \lstinline|m| on Line \ref{line:strcall}.
This time, the \lstinline|instanceof| check succeeds, because \lstinline|other| in this case \emph{is} a \lstinline|MyFoo|,
so the method (successfully) casts the \lstinline|other| argument to \lstinline|MyFoo|.
Since \lstinline|MyFoo| is declared as extending \lstinline|Foo<X>|, this is a valid result for the function.
Thus the \lstinline|Foo<Integer>| that was passed as the second argument on Line \ref{line:strcall} is returned
as a \lstinline|Foo<String>|.

Clearly this is wrong, because there are now two aliased variables of incompatible types; consequently, the later code fails (we discuss the failure point later).
The description of execution above employed some (here, intentionally) sloppy reasoning to parallel the checks in the Java compiler.
\begin{itemize}
\item The \lstinline|instanceof| check could have been statically flagged.
\item The cast could have been statically flagged.
\item The \lstinline|instanceof| could have returned false in the second invocation, since it was used on a \lstinline|MyFoo| from a different generic parameter instantiation
\item The case could have failed, again because it was used on a \lstinline|MyFoo| from a different generic parameter instantiation
\end{itemize}
Unfortunately two key factors lead to Java accepting this code and only incidentally discovering the problem later:
\begin{enumerate}
    \item Java implements generics by erasure. So the runtime representation of \lstinline|MyFoo| doesn't differ across the two calls. No information is kept around to distinguish the two classes of \lstinline|MyFoo|. This rules out the dynamic solutions.
    \item The Java compiler does not treat \lstinline|MyFoo| as generic. Attempts to cast to, or use \lstinline|instanceof| with \lstinline|Foo<Integer>| are statically flagged specifically because erasure means the generic parameters cannot be dynamically checked. But because \lstinline|MyFoo| \emph{syntactically} lacks generic parameters of its own, the compiler treats it as \emph{non-generic} and allows the \lstinline|instanceof| and cast without complaint.
\end{enumerate}
\mjnote{precise behaviour (JDK 26): from \texttt{Object}, \texttt{o instanceof Foo<Integer>} is a compile-time error (since Java 16; before that every non-reifiable \texttt{instanceof} target is an error), while the cast \texttt{(Foo<Integer>)o} is an unchecked warning; \texttt{instanceof} never warns. From a type that determines the argument (\texttt{Foo<Integer>} out of a \texttt{Bar<List<Integer>{}>} when \texttt{Foo<T> extends Bar<List<T>{}>}) both are accepted silently. The hole is that \texttt{MyFoo} is reifiable, so both forms are accepted with no warning. Item 2 and the list above can be restated in these terms.}

Subtler still is the actual cause of the failure. The two \lstinline|println| calls actually dispatch to different overloads:
the first to a version accepting an \lstinline|Object|, and the second to the more specific overload expecting a \lstinline|String|.
It is in fact the passage of a value from a generic API to the specific overload which causes the Java compiler to insert
a \lstinline|checkcast| in the generated bytecode.


It is tempting to accept this as a quirk of Java, which is already known to have other unsoundness~\cite{amin2016java}.
However this problem is broader in both scope and impact, as we show in the rest of the paper.
This issue affects all statically typed languages on the JVM, including Scala and Kotlin.
It also propagates to other compilation targets for JVM languages, including Scala Native~\todo{cite}
and GraalVM's Native Image support.


In the remainder of this paper:
\begin{itemize}
\item We detail the breadth of the problem (surveying forms that use class generics rather than methods generics, closures, and other manifestations), and how it is handled by various existing language implementations
\item We develop a core language modelling Java's generics, method-local classes and type tests, and show that typing method-local classes as Java does is unsound.
\item We develop a new type system mechanism for systematically tracking would-be implicit dependence of a
method-local class on generic parameters, and show that it soundly prevents the problem.
\end{itemize}

\section{Scope of the Problem}
This problem arises in essentially all JVM languages, all of which must interact with Java and have therefore chosen to also support method-local classes.

\subsection{Generic Reification} A natural suspicion is that this is ``simply'' a problem with generic erasure, that of course a language that cannot distinguish generic instantiations of a class at runtime will have difficulties of this sort.
There is some truth to this: Java is permitting a cast that it cannot actually check due to type erasure.
However there is more to it than that: Java will eagerly flag code such as \lstinline|(List<String>)(new LinkedList<Integer>())|.
So the language does intend to warn about uses of uncheckable casts.
\mjnote{\texttt{(List<String>)(new LinkedList<Integer>())} is an incompatible-types error, not an unchecked one. The contrast that matters here: an unchecked cast is a warning, an unchecked \texttt{instanceof} is an error.}
And while reified generics do provide enough information to check casts dynamically, only certain forms of reification
make correct casts straightforward.

In a language which implements parametric polymorphism by templating / heterogeneous compilation
(C++, C\#, or early experiments with generic Java~\cite{agesen1997adding}), the check is straightforward:
each instantiation of \lstinline|m| with different generic parameters is compiled separately, resulting in separate
class declarations for each instantiation.
Consider reinterpreting Figure \ref{fig:original_example} in C++ as in Figure \ref{fig:cpp}.
\texttt{gcc} reports for Line \ref{line:cpp_err}:
\begin{verbatim}
<source>:7:16: error: cannot 'dynamic_cast' 'other' (of type 'class Object*')
to type 'class m<Integer>(Object*, const Integer*)::MyFoo*' (source type is not polymorphic)
    7 |     MyFoo* d = dynamic_cast<MyFoo*>(other);
      |                ^~~~~~~~~~~~~~~~~~~~~~~~~~~
\end{verbatim}
\todo[inline]{not perfect, because this is C++ giving a static warning, not catching the error dynamically...}
Notice that the error message uses the instantiation of the method signature as a scope for a declaration of \lstinline|MyFoo|.
But heterogeneous compilation has subtle costs and wide-ranging consequences for language design, not just implementation,
and complex performance consequences~\cite{odersky2001two,kennedy2001design}. Even if this does fix the problem,
it is not universally appropriate.

An alternative, common conception of generic reification is to simply save the type parameters along with the
single implementations of classes, for it to be checked when needed. But note again that \lstinline|MyFoo|
has no generic parameters of its own. So a shallow check with this variant of reified generics is insufficient ---
each \lstinline|MyFoo| would need to contain a representation of, or reference to, its parent type's generic parameters.
And because this phenomenon is not limited to a single step in the inheritance hierarchy, the cast must traverse and compare
a substantial amount of data --- not a mere comparison of virtual table pointers. This again has multiple implementation
approaches, neither ideal (chains of parent type instantiations hurt cache locality, inlining data can bloat small instances).

So there remains a need to articulate a solution to this problem where generics are implemented via erasure.
\mjnote{under erasure, Java's checked-cast rule is already enough once the dependency of \texttt{MyFoo} on \texttt{X} is visible in its type, and that is what funnelling provides. This paragraph can lead straight into Section~3.}

\noindent
A program is a class table \decls and a main expression $e$.
We require the following well-formedness conditions:
\begin{enumerate}
    \item[(A1)] Class names are unique across top-level and local classes.
    \item[(A2)] Field names are unique across all classes.
    \item[(A3)] In a class, top-level or local, all method names are disjoint.
    \item[(A4)] Every $X$ and every $x$ other than \this is bound at most once in the program.
    \item[(A5)] No parameter and no variable of an \kw{if} is \this.
    \item[(A6)] In a list of funnels $\pl{F}$, all the funnelled type variables are disjoint.
    \item[(A7)] \decls contains $\subclass{\Object}{}{\Object}{}{}{}$, and the chain of superclasses of every other top-level class reaches \Object.
\end{enumerate}
Well-formedness requirements A1-A7 are common requirements, such as uniqueness of names.
To simplify scoping, requirement A4 asks for every name to be bound once in the whole program: there is no shadowing, and two methods never have a parameter with the same name.
A funnel $\funnel{X}$ does not bind $X$: it uses the type variable $X$ in scope.
A method of a local class binds \this, as in Java; this is the only form of shadowing.
Requirement A6 makes the substitutions of Figure~\ref{fig:substitution} well defined when their domain is a list of funnels.
Requirement A7 makes inheritance acyclic, except for \Object, which is its own superclass.
Thus rule \textsc{sub-inherit} can be applied to $\gen{\Object}{}$ forever, and rules \textsc{simpleFieldSuper} and \textsc{searchSuper} reduce a field access or a call on an \Object\ to itself.
This is harmless: our rules are not meant to be read as algorithms, and a well-typed expression never accesses a field or calls a method of \Object.
\\[1ex]
Well-formedness requirements B1-B3 below are about local classes:
\begin{enumerate}
    \item[(B1)] The main expression contains no local classes.
    \item[(B2)] Local classes cannot be extended: the superclass of every class, top-level or local, is a top-level class.
    \item[(B3)] In a local class $\innerobj{C}{\pl{F}}{C'}{\pl{T}}{\pl{e}}{\pl{M}}$, every funnelled type variable is in scope.
\end{enumerate}
Requirement B1 makes every local class occur in a method body, so that the type variables in scope where it is written are defined.
Requirements B2 and B3 are enforced by the type system, but we call them out because they are explicit design choices.

By well-formedness requirements A1 and B1, a class name $C$ identifies at most one $K$ with $\declared{K}$.
For a class type $\gen{C}{\pl{T}}$, $\mathsf{scope}(\gen{C}{\pl{T}})=\Delta_0;\pl{T}''$ gives the bounds $\Delta_0$ of the type variables that the methods of $C$ see, without the type variables of the methods themselves.
It also gives the types $\pl{T}''$ that the arguments $\pl{T}$ assign to the type variables in $\Delta_0$.
For a top-level class, $\Delta_0$ is the bounds of the class and $\pl{T}''=\pl{T}$.
For a local class $C_0$ with funnels $\pl{F}$, the bounds $\Delta',\Delta''$ are the bounds of the type variables in scope where $C_0$ is written.
For a type variable $X$, $\Delta(X)$ is the bound of $X$ in $\Delta$, and $\mathrm{cod}(\Delta)$ is the sequence of the bounds in $\Delta$.
The function $\mathsf{scope}(\Delta;\pl{F};\pl{T})$ goes through the funnels $\pl{F}$ and the arguments $\pl{T}$ together, one position at a time, where $\emptyset$ is the empty sequence.
At the position of a funnel $\funnel{X}$, it adds $\ext{X}{\Delta(X)}$ to the bounds and the argument to the types.
At the position of a ground funnel $G$, the argument must be $G$ itself, and nothing is added.
The operator $\cdot$ concatenates two results of $\mathsf{scope}$, component by component.
An expression $e'$ occurs in $e$ when $e=\mathcal{C}[e']$, for a context $\mathcal{C}$ of Figure~\ref{fig:contexts}.
Contexts $\mathcal{C}$ do not enter the methods of a local class; thus $\mathsf{scope}(\gen{C}{\pl{T}})$ has at most one value.
The reduction of Figure~\ref{fig:opsem} uses the values $v$ and the evaluation contexts $\mathcal{E}$ of Figure~\ref{fig:contexts}.
\\[1ex]
Rules \textsc{simpleFound} and \textsc{innerFound} use the method $\mathsf{fresh}(M)$:
the method $M$ where every type variable and every variable bound in $M$ is renamed into a fresh name, that is a name occurring nowhere in the program and in the reduced expression.
The type variables and variables bound in $M$ are the type variables of its signature, its parameters, and, inside its body, the variable of every \kw{if} and the type variables and parameters of every method of a local class.
The variable \this is never renamed.
Renaming is needed because a value of a local class carries the code of its methods.
For example, consider a local class \QQ{L} whose method \QQ{m} has a parameter \QQ{x} and calls \QQ{m} on a captured value of class \QQ{L}.
The body of a call of \QQ{m} then contains the captured value, and the captured value contains a copy of the method \QQ{m} binding \QQ{x} again.
Without renaming, rule \textsc{innerFound} would replace \QQ{x} also in the method \QQ{m} of the captured value.
With renaming, the domain of every substitution during reduction contains only fresh names or names bound in the main expression.
By requirements A4 and B1, no value binds a name bound in the main expression.
Thus a substitution never reaches a type variable or a variable bound inside the substituted expression.

Substitution replaces every occurrence of a type variable, \emph{including} the ones in the method signatures of a method-local class.
Substitution does not rename the type variables it meets.
No renaming is needed: the substituted types are ground, and the domain of the substitution never contains a type variable bound inside the substituted term, by requirement A4 in the program and by $\mathsf{fresh}$ during reduction.
In the domain of a substitution, bounds $\Delta$ stand for $\mathrm{dom}(\Delta)$, and funnels $\pl{F}$ stand for their funnelled type variables:
$\tsubst{T}{F_1\ldots F_n}{T_1\ldots T_n}$ replaces $X_i$ with $T_i$ for every $F_i=\funnel{X_i}$, and ignores every $F_i=G_i$.
Substitution of type variables into expressions happens only during reduction, where the substituted types are ground.
Thus $\tsubst{\funnel{X_i}}{X_1\ldots X_n}{T_1\ldots T_n}=T_i$ is a ground type $G$, and the result is again a funnel.

The rule \textsc{new-local} is the heart of funneling, including subtle management of type environments.
The management of type environments in \textsc{new-local} is subtle. The rule constructs a restricted set of type bounds and variable bindings reflecting only the explicitly-funnelled type variables:
$\Delta'$ includes only the explicitly-funnelled type variables, and $\Gamma'$ keeps only the variables of $\Gamma$, other than \this, whose types mention only type variables of the result type $\gen{C}{|\pl{F}|}$ (which must be well-kinded under $\Delta'$).
The bounds $\Delta'$ are computed by $\mathsf{scope}(\Delta;\pl{F};|\pl{F}|)$, which is undefined when a funnelled type variable is not in $\Delta$.
However, the rule still uses the \emph{full} ambient environments for checking certain subexpressions. This is because some $e\in\pl{e}$ may initially contain uses of \emph{non}-funnelled type variables (e.g., an explicit call), but will reduce to a value which no longer depends on such type variables.
This is why the premise $\typing{\Delta}{\Gamma}{\obj{C'}{\pl{T}}{\pl{e}}}{\_}$ checks the effective supertype instance under $\Delta;\Gamma$, but the premise $\kind{\Delta'}{\gen{C'}{\pl{T}}}$ ensures the resulting type of that
expression satisfies the funnelling constraints by checking kinding under the more restrictive $\Delta'$.

Rule \textsc{new-local-java} of Figure~\ref{fig:java} types local classes as Java does.
A local class has no funnels, and its methods are typed under the full $\Delta$ and $\Gamma$ in scope, except for \this.
Replacing rule \textsc{new-local} with rule \textsc{new-local-java} makes our system unsound for the same reason Java is unsound.
Consider the method \QQ{mk} below, the method \QQ{m} of Figure~\ref{fig:original_example} in our syntax:
\begin{lstlisting}
<X> Foo<X> mk(Object<> other, X x){ return
  if (other instanceof MyFoo<> w){ w }
  else { new MyFoo<> extends Foo<X>(){ X x(){ return x; } } }; }
\end{lstlisting}
Rule \textsc{new-local-java} gives to the object created by \QQ{mk} the type \QQ{MyFoo<>}.
Rule \textsc{sub-inherit-local} reads the declaration of \QQ{MyFoo}, so \QQ{MyFoo<>} is a subtype of \QQ{Foo<X>}, where \QQ{X} is the type variable of \QQ{mk}.
The type \QQ{MyFoo<>} does not say which type \QQ{X} stood for when the object was created.
Since $\generic{\QQ{MyFoo}}=\QQ{MyFoo<>}$ has no type variables, rule \textsc{cast-down} accepts the type test \QQ{other instanceof MyFoo<>} from \QQ{Object<>}.
Thus the call \QQ{a.<String>mk(a.<Integer>mk(o, i), s)} has type \QQ{Foo<String>}, but it returns a \QQ{Foo<Integer>}.
This is the unsoundness of Java.
It is there even if we keep the restriction of Java that the name of a local class can only be written inside the method declaring it, as \QQ{mk} does.
Our formal system shows two more failure points.
They are the same failure, shown more explicitly:
\begin{itemize}
\item Reduction does not preserve types, even without type tests.
The call \QQ{a.<Integer>mk(o, i)} has type \QQ{Foo<Integer>}.
It reduces to the value
\begin{lstlisting}
new MyFoo<> extends Foo<Integer>(){ Integer x(){ return i; } }
\end{lstlisting}
The type of this value is \QQ{MyFoo<>}, a subtype of \QQ{Foo<X>} but not of \QQ{Foo<Integer>}.
Java has no typing of values during reduction, so in Java this failure is invisible.
\item Typing depends on the names of type variables.
Our system lets the name of a local class be written anywhere.
Requirement A4 forbids the same type variable name in two methods; without requirement A4, consider the methods
\begin{lstlisting}
<Y> MyFoo2<> mk2(Y y){
  return new MyFoo2<> extends Foo<Y>(){ Y x(){ return y; } }; }
<Y> Foo<Y> leak(MyFoo2<> z){ return z; }
\end{lstlisting}
The method \QQ{leak} is well typed, since the type variable \QQ{Y} of \QQ{leak} has the same name as the type variable \QQ{Y} of \QQ{mk2}.
Renaming \QQ{Y} into \QQ{Z} in \QQ{leak} makes \QQ{leak} ill typed.
The call
\begin{lstlisting}
a.<String>leak(a.<Integer>mk2(i))
\end{lstlisting}
has type \QQ{Foo<String>}, but it returns a \QQ{Foo<Integer>}, without type tests.
Under rule \textsc{new-local-java}, this is one more reason for requirement A4.
\end{itemize}
Funnelling solves the problem in all three forms.
Under rule \textsc{new-local}, the object created by \QQ{mk} has type \QQ{MyFoo<X>}, written \QQ{new MyFoo<X funnel> extends Foo<X>()\{..\}}.
Since $\generic{\QQ{MyFoo}}=\QQ{MyFoo<X>}$, rule \textsc{cast-down} accepts the type test \QQ{instanceof MyFoo<X>} from \QQ{Foo<X>}, but not from \QQ{Object<>}.
The call \QQ{a.<Integer>mk(o, i)} reduces to a value of type \QQ{MyFoo<Integer>}, a subtype of \QQ{Foo<Integer>}.

\section{(Un)Soundness of Method Local Classes}
With our language primitives in place, we now consider type safety of two variants of our language.
The two variants differ only in the typing of local classes:
\begin{enumerate}
\item $\zeta(\mathsf{Java})$ types local classes with rule \textsc{new-local-java} of Figure~\ref{fig:java}, as Java does;
\item $\zeta(\mathsf{funnelled})$ types local classes with rule \textsc{new-local} of Figure~\ref{fig:typing}.
\end{enumerate}
Both variants use the type test of Java:
rule \textsc{if-instanceof} accepts only checked casts (Figure~\ref{fig:cast}), and at run time rules \textsc{ifThen} and \textsc{ifElse} compare class names only.
As shown in Section~\ref{sec:core}, $\zeta(\mathsf{Java})$ is unsound.
We now show that $\zeta(\mathsf{funnelled})$ is sound.

\section{Related Work}
It is not uncommon to have ``intentional unsoundness'' in industrial languages,
such as Java's covariant array subtyping, or TypeScript's covariant method subtyping.
However these are intentionally designed into the language to improve ease of use, and in most cases (like Java's array handling)
problematic uses are detected at runtime (e.g., Java checks upon storing into an array that the new entry value
is a subtype of the array's original content type).

However, unintentional unsoundness in industrial type systems is rarer.
The most notable example is Amin and Tate's discovery~\cite{amin2016java} that Java and Scala's handling of generic type constraints
was rendered unsound by the fact that \lstinline|null| is treated as inhabiting all reference types, making all
type constraints (even nonsensical ones) satisfiable.
Servetto et al.~\cite{unsound_presentation} first pointed out the issue publicly, though in the 
Q\&A session after the talk, multiple Java designers were unsurprised --- as Gilad Bracha put it, ``Once I saw the title of your talk, I understood what the problem was.''

The key issues at work in the interaction of method-local inner classes and generics arise from the interaction of (1) nominal dynamic downcasts, (2) design choices about what runtime information about generic parameters is both persisted \emph{and checked} by casts, and (3) (not) tracking all dependencies on type parameters in the type system.
Essentially, Java and Scala both treat \lstinline|MyFoo| as a sort of existential type --- that there exists some \lstinline|X|  such that
\lstinline|MyFoo| extends \lstinline|Foo<X>|. However, treating \lstinline|MyFoo| as a closed rather than generic type is equivalent
to assuming that there is only one existential for all instances --- associated with the declaration site --- rather than potentially
different existentials for different instances. This combined with the fact that the JVM is unable to dynamically check for different instantiations
leads to the unsoundness.
Our dynamic solution resolves this with a specific implementation of casts on reified generics.
\mjnote{under modern Java there is no separate dynamic solution; see the note on the dynamic approach in the introduction.}
Our static solution effectively prohibits the de facto existential capture of the enclosing type parameter.

public interface CheckedFunction<T, R> { R apply(T t) throws Exception; }
@SuppressWarnings("unchecked")
public static <T, E extends Exception> T sneakyThrow(Exception e) throws E {
    throw (E) e;
}

public static <T, R> Function<T, R> unchecked(CheckedFunction<T, R> checkedFunction) {
    return t -> {
        try {
            return checkedFunction.apply(t);
        } catch (Exception e) {
            return sneakyThrow(e);
        }
    };
