\section{A Core Language for Funnelling}
\label{sec:core}
% Metavariables are the letters of the grammar (X, T, C, e, Delta, Gamma, ...), decorated only with primes and digit subscripts:
% X, X', X'', X0, X3.
% The other subscripts are the indices of a sequence: X_i is the element at position i of X_1...X_n, and Xs is X_1...X_n.

We now present the core language of Section~\ref{sec:funnelling}: its syntax, its small step reduction and its type rules.
The type rules encode funnelling.
Replacing the type rule \textsc{newLocal} with rule \textsc{newLocalJava} gives the Java typing of local classes.

Figure \ref{fig:syntax} gives the syntax of our core language.
An expression is a variable $x$, a method call $\call{e}{\pl{T}}{m}{\pl{e}}$, a super call $\explicitcall{e}{T}{\pl{T}}{m}{\pl{e}}$, a field access $e\fstop f$, an object creation $\obj{C}{\pl{T}}{\pl{e}}$ of a top-level class, a local class $\innerobj{C}{\pl{F}}{C'}{\pl{T}}{\pl{e}}{\pl{M}}$ or a type test $\ifthen{e_0}{T}{x}{e_1}{e_2}$.\footnote{The syntax \Q@if (a instanceof B c)@ is valid Java since Java 16.}
As in FJ, \Q@this@ is just a special case of a variable $x$.
A method call $\call{e}{\pl{T}}{m}{\pl{e}}$ calls the method $m$ on the receiver $e$, with type arguments $\pl{T}$ and arguments $\pl{e}$.
A super call $\explicitcall{e}{T}{\pl{T}}{m}{\pl{e}}$ searches for the method $m$ starting from the class of the type $T$, instead of from the class of the receiver $e$.
That is, a super call works as a flexible kind of Java \Q@super@ call, attempting to call the method $m$ as if the receiver were of the supertype $T$.
An object creation $\obj{C}{\pl{T}}{\pl{e}}$ creates an instance of the top-level class $\gen{C}{\pl{T}}$.
The first arguments of $\pl{e}$ initialize the fields of $C$; the other arguments are the arguments of the object creation of the superclass of $C$.
A local class $\innerobj{C}{\pl{F}}{C'}{\pl{T}}{\pl{e}}{\pl{M}}$ declares the local class $C$ and creates an instance of $C$.
The type test $\ifthen{e_0}{T}{x}{e_1}{e_2}$ reduces to $e_1$, with $x$ bound to the value of $e_0$, when the class of the value of $e_0$ is the class of $T$ or a subclass of the class of $T$; otherwise the type test reduces to $e_2$.

A type is a class type $\gen{C}{\pl{T}}$ or a type variable $X$.
A ground type $G$ is a type with no type variables.
A ground type is the equivalent of a value, but at the type level.

A program is a class table \decls and a main expression $e$.
The funnels $\pl{F}$ serve a double role.%
\footnote{A Java method-local class can declare type variables of its own: \Q@class Local<Y>\{..\}@, declared inside a method \Q@<X> m(..)@, would juggle \Q@Y@ (declared by \Q@Local@) and \Q@X@ (captured from \Q@m@).
To keep a tight focus in our paper, our local classes do not declare type variables of their own.}
From the perspective of the inside of the local class (the methods $\pl{M}$), the funnels $\pl{F}$ select the type variables in scope that are visible in the local class.
From the perspective of the \Q@new@ expression itself, the funnels $\pl{F}$ instantiate those type variables, forming the actual type of the created instance.

To allow a local class instance to exist in the main expression (e.g., during reduction), a funnel is either a ground type $G$ or a funnelled type variable $\funnel{X}$.
In \decls, all the funnels are of the form $\funnel{X}$, by well-formedness requirement A11 (discussed shortly).
In the main expression, outside of the methods of local classes, all the funnels are of the form $G$, by A12: there, no type variable is in scope.
When a local class is nested in a method of a local class in the main expression, a mixture of funnels $\funnel{X}$ and $G$ can be present.

A local class has no fields: the arguments $\pl{e}$ are the arguments of the object creation of the superclass $C'$.
The methods $\pl{M}$ of a local class can use only the funnelled type variables, and the variables in scope other than \Q@this@ whose types mention only funnelled type variables.

The conventional type environment $\Gamma$ gives a type to each variable that the expression can use.
Bounds $\Delta$ give an upper bound to each type variable that the expression can use.
A declaration $\subclass{C}{\Delta}{C'}{\pl{T}}{\pl{M}}{\pl{S}}$ declares the top-level class $C$ with the type variables bounded by $\Delta$, the supertype $\gen{C'}{\pl{T}}$, the methods $\pl{M}$ and the fields/slots $\pl{S}$.
A method $\method{\Delta}{T_0}{m}{T_1\gap x_1,\ldots,T_n\gap x_n}{\ret{e}}$ has the type variables bounded by $\Delta$, the return type $T_0$, the parameters $x_1,\ldots,x_n$ and the body $e$.
Every method has a body; for simplicity, as in FJ, there are no abstract methods.
A class declaration $K$ is either a top-level declaration $\mathsf{Dec}$ or a local class.
The name of a local class can be written anywhere in the program, for example as the return type of a method; in Java, the name of a method-local class can be written only inside the method declaring it.
Funnelling is sound without the restriction of Java (Section~\ref{sec:soundness}), and thus also with that restriction.

Evaluation contexts $\mathcal{E}$ fix the order of evaluation, left to right call-by-value, used by the reduction.

We require the following well-formedness constraints on valid programs:
\begin{itemize}
    \item (A1)  In \decls, class names are unique across top-level and local classes.
    \item (A2)  In a class, all the field names, including in superclasses, are distinct.
    \item (A3)  In a class, whether top-level or local, all the method names are distinct.
    \item (A4)  In a method, all the parameter names $x_1,\ldots,x_n$ are distinct.
    \item (A5)  In a type environment $\Delta$, all the $X$ in $\mathrm{dom}(\Delta)$ are distinct.
    \item (A6)  In a list of funnels $\pl{F}$, all the $X$ in $\mathrm{dom}(\pl{F})$ are distinct.
    \item (A7)  There is no shadowing of $X$ or $x$, except for \Q@this@.\footnote{A method body of a local class also binds \Q@this@, thus shadowing the \Q@this@ of the enclosing method.}
    \item (A8)  In the syntax \ifthen{\_}{T}{x}{\_}{\_}, $x$ is not \Q@this@, and \Q@this@ does not appear as a method parameter name.
    \item (A9)  \decls contains $\subclass{\Object}{}{\Object}{}{}{}$, and the chain of superclasses of every other top-level class reaches \Q@Object@.
    \item (A10)  In \decls, the superclass of every class, top-level or local, is a top-level class.
    \item (A11)  In \decls, every funnel is of the form $\funnel{X}$.
    \item (A12)  The main expression has no free variable and no free type variable.
\end{itemize}
Well-formedness requirements A1-A10 and A12 are common requirements, such as uniqueness of names.
A11 is the requirement on funnels discussed above.

An expression $e'$ occurs in $e$ when $e=\mathcal{C}[e']$, for an expression context $\mathcal{C}$.
By well-formedness requirement A1, a class name $C$ identifies at most one $K$ with $\declared{K}$.
$M\in K$ holds when $M$ is a method of the class declaration $K$, top-level or local.
$M\in C$ holds when $M$ is a method of the declared class $C$, top-level or local.
For a top-level class $C$ with bounds $\Delta$, $\mathsf{scope}(C)=\Delta$; with the type arguments $\pl{T}$ of a type $\gen{C}{\pl{T}}$, this recovers (effectively) a type substitution which can be used with methods of the class.
For a local class $C_0$ with funnels $\pl{F}$, $\mathsf{scope}(C_0)=\Delta_0$, where $\Delta_0$ holds, in the order of $\mathrm{dom}(\pl{F})$, the bound $\ext{X}{T}$ in $\Delta,\Delta'$ of each $X\in\mathrm{dom}(\pl{F})$, where $\Delta'$ are the bounds of the method $m$ declaring $C_0$ and $\mathsf{scope}(C)=\Delta$ for the class $C$ of $m$. Note that $m$ could be a method of either a top-level or local class.
$\tsubst{T}{\Delta}{\pl{T}}$ is the simultaneous substitution, defined only when $\Delta$ and $\pl{T}$ have the same length.
A simultaneous substitution, of types or of values, is defined only when the names in its domain are distinct.
\\[1ex]
For a type variable $X$, $\Delta(X)$ is the bound of $X$ in $\Delta$.
$\mathrm{dom}(\Delta)$ is the sequence of the type variables in $\Delta$, and $\mathrm{cod}(\Delta)$ is the sequence $T_1,\ldots,T_n$ of $\Delta=\ext{X_1}{T_1},\ldots,\ext{X_n}{T_n}$.
For a variable $x$, $\Gamma(x)$ is the type of $x$ in $\Gamma$.
$\mathrm{dom}(\pl{F})$ is the sequence of the $X$ such that $\funnel{X}$ is in $\pl{F}$.
$\ftv{T}$ is the set of the type variables occurring in $T$.
A function or a judgement applied to sequences stands for one application at every position, and requires the sequences to have the same length:
$|F_1,\ldots,F_n|$ is $|F_1|,\ldots,|F_n|$;
$\ftv{T_1,\ldots,T_n}$ is $\ftv{T_1}\cup\ldots\cup\ftv{T_n}$;
$\kind{\Delta}{T_1,\ldots,T_n}$ is $\kind{\Delta}{T_1}\quad\ldots\quad\kind{\Delta}{T_n}$;
$\subtype{\Delta}{T_1,\ldots,T_n}{T'_1,\ldots,T'_n}$ is $\subtype{\Delta}{T_1}{T'_1}\quad\ldots\quad\subtype{\Delta}{T_n}{T'_n}$;
$\typing{\Delta}{\Gamma}{e_1,\ldots,e_n}{T_1,\ldots,T_n}$ is $\typing{\Delta}{\Gamma}{e_1}{T_1}\quad\ldots\quad\typing{\Delta}{\Gamma}{e_n}{T_n}$.
$m\not\in\pl{M}$ holds when no method in $\pl{M}$ has name $m$, and $\mathrm{names}(\pl{M})$ is the set of the names of the methods in $\pl{M}$.
$\Gamma\setminus x$ is $\Gamma$ without the variable $x$.
For a set of type variables $\pl{X}$, $\Gamma|_{\pl{X}}$ keeps the variables $T\gap x$ of $\Gamma$ such that $\ftv{T}\subseteq\pl{X}$.

Rules \textsc{topFieldFound}, \textsc{topFieldSuper} and \textsc{localFieldSuper} read a field.
Rule \textsc{topFieldFound} reads a field declared by the class of the object.
Rule \textsc{topFieldSuper} reads a field not declared by the class $C$ of the object from the object of the superclass of $C$, made of the remaining values.
A local class declares no fields, so rule \textsc{localFieldSuper} reads every field from the object of the superclass.

Rules \textsc{ifThen} and \textsc{ifElse} test the class of the value $v$ against the class $C'$ of the type test, ignoring the type arguments $\pl{T}$ of $\gen{C'}{\pl{T}}$.
Rule \textsc{ifThen} reduces to $e'_1$ with $x$ replaced by $v$, where $e'_1$ is $e_1$ renamed by $\mathsf{fresh}$; rule \textsc{ifElse} reduces to $e_2$.
They rely on the metafunction
{\small
\begin{Define}{\mathsf{typeOf}(v)=G}
\mathsf{typeOf}(v)=\gen{C}{\pl{G}}\\
\quad\textrm{where }v\in\{\obj{C}{\pl{G}}{\_},\innerobj{C}{\pl{G}}{\_}{\_}{\_}{\_}\}
\end{Define}
}

Rules \textsc{topAddSuper}, \textsc{topFound}, \textsc{localFound}, \textsc{localSuper} and \textsc{searchSuper} call a method.
Rule \textsc{topAddSuper} turns a call on an object of a top-level class into a super call starting from the class of the object.
Rule \textsc{topFound} runs the method $m$ found in the class of a super call, replacing the type variables of the class and of the method, \Q@this@ and the parameters.
Rule \textsc{localFound} runs the method $m$ found in a value of a local class; the funnelled type variables are already replaced in that value, so only the type variables of the method are replaced.
Rule \textsc{localSuper} turns a call on a value of a local class without the method $m$ into a super call starting from the superclass of the local class.
Rule \textsc{searchSuper} moves a super call to the superclass when the class does not declare $m$.
Rule \textsc{ctx} reduces inside an evaluation context.

Rules \textsc{ifThen}, \textsc{topFound} and \textsc{localFound} also use the relation $\mathsf{fresh}$.
The names bound in an expression $e$ are the variable of every type test occurring in $e$, and the names bound in every method of a local class occurring in $e$.
The names bound in a method $M$ are the type variables of its signature, its parameters, and the names bound in its body.
$\mathsf{fresh}(e,e')$ holds when $e'$ is $e$ with the names bound in $e$ renamed: $e$ and $e'$ are equal up to the names of their binders (i.e., $\alpha$-equivalent).
$\mathsf{fresh}(M,M')$ holds when $M'$ is $M$ renamed in the same way.
The variable \Q@this@ is never renamed.
Renaming is needed because a value of a local class carries the code of its methods, and reentrancy between methods would result in shadowed bindings without renaming.\footnote{This is the same familiar issue from various lambda calculi. Object-oriented languages often avoid this by heap-allocating objects, so substitution inserts locations rather than full object bodies. But value-oriented object calculi face the same issue in a different guise.}
For example, consider a local class \Q@L@ whose method \Q@m@ has a parameter \Q@x@ and calls \Q@m@ on a captured value \Q@y@ of class \Q@L@:
\begin{lstlisting}
Object<> k(L<> y){ return
  new L<> extends Object<>(){ Object<> m(Object<> x){ return y.m(x); } }; }
\end{lstlisting}
In a call of \Q@k@ with a value \Q@v@ of class \Q@L@, the body of \Q@m@ becomes \Q@v.m(x)@, and the method \Q@m@ of \Q@v@ binds \Q@x@ again.
Without $\mathsf{fresh}$, the substitution would attempt to place a binder of a name under a binder of the same name, breaking well-formedness requirement A7.

Figure \ref{fig:typing} gives the typing rules for the core language, which use funnelling to restore type safety.
Rule \textsc{subs} is subsumption, where the supertype $T_2$ must be well-kinded (described in the next section). Rule \textsc{var} reads the type of a variable from $\Gamma$.
Rule \textsc{field} types the access to a field declared by the static class $C$ of the receiver, and rule \textsc{call} types the call of a method declared by the class $C_0$ of the receiver.
In rule \textsc{call}, $\mathsf{scope}$ gives the type variables of $C_0$, the type arguments $\pl{T}_0$ of the receiver replace them, and the type arguments $\pl{T}_1$ of the call must satisfy the bounds of $m$.
Rule \textsc{superCall} types a super call $\explicitcall{e_0}{\gen{C}{\pl{T}}}{\pl{T}_1}{m}{e_1,\ldots,e_n}$: the receiver $e_0$ has type $\gen{C}{\pl{T}}$, the class $C$ is a top-level class, and the signature of $m$ is read from a class $C_0$ declaring $m$, where $C_0$ is $C$ or a superclass of $C$.
Rule \textsc{newObject} types the creation of an \Q@Object@.
We need this dedicated rule: \Q@Object@ extends \Q@Object@ (A9), so typing \Q@new Object<>()@ with rule \textsc{newTop} would need an infinite derivation.
Rule \textsc{newTop} types the creation of an object of another top-level class $C$: the first arguments have the types of the fields of $C$, and the other arguments are typed as an object creation of the superclass of $C$.
\looseness=-1

Rule \textsc{newLocal} is the heart of funnelling.
The rule constructs restricted bounds and a restricted type environment, reflecting only the funnelled type variables:
$\Delta'$ includes only the funnelled type variables, and $\Gamma|_{\ftv{|\pl{F}|}}\setminus\this$ keeps only the variables of $\Gamma$, other than \Q@this@, whose types mention only type variables of the result type $\gen{C}{|\pl{F}|}$ (which must be well kinded under $\Delta'$).
The bounds $\Delta'$ are $\Delta|_{\pl{F}}$, which is undefined when a funnelled type variable is not in $\Delta$.
The premise $\ftv{\mathrm{cod}(\Delta')}\subseteq\mathrm{dom}(\Delta')$ requires the bounds of the funnelled type variables to mention only funnelled type variables.
However, the rule still uses the \emph{full} $\Delta$ and $\Gamma$ for typing the arguments $\pl{e}$. This is because some $e\in\pl{e}$ may initially contain uses of \emph{non}-funnelled type variables (e.g., in the type arguments of a method call), but will reduce to a value which no longer depends on such type variables.
This is why the premise $\typing{\Delta}{\Gamma}{\obj{C'}{\pl{T}}{\pl{e}}}{\_}$ types the object creation of the superclass $\obj{C'}{\pl{T}}{\pl{e}}$ under $\Delta;\Gamma$, but the premise $\kind{\Delta'}{\gen{C'}{\pl{T}}}$ checks the supertype $\gen{C'}{\pl{T}}$ under the more restrictive $\Delta'$.

The funnelled type variables are a subset of the type variables in scope: $\mathrm{dom}(\Delta')\subseteq\mathrm{dom}(\Delta)$.
The premises of rule \textsc{newLocal} require only that this subset holds every type variable that the local class uses.
This is how funnelling lies between the granularities (1) and (2) of Section~\ref{sec:funnelling}.
Rule \textsc{newLocalJava} puts no type variable in the type of a local class: this is granularity (1).
A rule requiring $\mathrm{dom}(\Delta')=\mathrm{dom}(\Delta)$ would give granularity (2): every local class would have to funnel all the type variables in scope, also the type variables that the local class does not use, as Kotlin does (Section~\ref{sec:impact}).

A local class appears in two kinds of places:
(1) The (original) declaration of the local class is written in the body of a method of a top-level class, possibly nested inside other local classes.
(2) Copies of the local class can be in the main expression: reduction copies the declaration from the class table into the main expression, possibly inside the methods of another copy, renaming its bound names by $\mathsf{fresh}$, replacing type variables with types and variables with values.
The relation $K\gap\mathsf{consistent}$ ensures that copies in the second case are consistent with the original declaration.
\begin{Define}{K\gap\mathsf{consistent}}
\innerobj{C}{\pl{F}}{C'}{\pl{T}}{\pl{e}}{\pl{M}}\gap\mathsf{consistent}\\
\quad\textrm{where }\declared{\innerobj{C}{\pl{F}'}{C'}{\pl{T}'}{\_}{\pl{M}'}}\\
\quad\phantom{\textrm{where }}\mathsf{scope}(C)=\Delta_0\\
\quad\phantom{\textrm{where }}\pl{T}=\tsubst{\pl{T}'}{\Delta_0}{|\pl{F}|}\\
\quad\phantom{\textrm{where }}\mathrm{names}(\pl{M}')=\mathrm{names}(\pl{M})\\
\quad\phantom{\textrm{where }}\mathsf{overrideOk}(\gen{C}{|\pl{F}|},\pl{M})
\end{Define}
$K\gap\mathsf{consistent}$ trivially holds for case (1). For case (2), the first condition of the definition finds the declaration of $K$.
The supertype and the method signatures of $K$ must be those of the declaration, with the funnelled type variables of $\pl{F}'$ replaced by $|\pl{F}|$, up to the names of the type variables of each method.
$K$ and the declaration have the same method names.
The bodies of the methods of $K$ are not required to be those of the declaration: the main expression can hold a local class whose method bodies differ from the declaration, and rule \textsc{newLocal} types those method bodies.
Rules \textsc{call}, \textsc{subInheritLocal}, \textsc{kindClass} and \textsc{castDown}, the relation $\mathsf{consistent}$ and $\mathsf{overrideOk}(T,M)$ read the declaration, while the reduction runs the methods of the copy.

Rule \textsc{ifInstanceof} accepts the type test $\ifthen{e_0}{T}{x}{e_1}{e_2}$ only when $\cast{\Delta}{T_0}{T}$, where $T_0$ is a type of $e_0$.
The relation $\cast{\Delta}{T}{T'}$ is the \emph{checked cast}: a type test against $T'$ on a value of static type $T$ is decided by the class of the value alone.
Rule \textsc{castUp} accepts a target $T'$ that is a supertype of the source $T$.
Rule \textsc{castVar} replaces a source type variable $X$ with the bound of $X$.
Rule \textsc{castDown} accepts a target $\gen{C}{\pl{T}}$ that is a subtype of the source $\gen{C'}{\pl{T}_0}$, \emph{when the source determines the type arguments} $\pl{T}$.\footnote{This is the condition under which a Java cast to a parameterized type is checked~\cite[Section~5.1.6.2]{jls}~\cite{bracha1998making}.
When the source does not determine the type arguments, Java rejects the type test \Q@e instanceof C<Ts>@, but accepts the cast \Q@(C<Ts>)e@ with an unchecked warning: at run time, that cast checks only the class \Q@C@.\looseness=-1}
$\gen{C}{\mathrm{dom}(\Delta_0)}$ is the class $C$ instantiated with its own type variables, and $\gen{C'}{\pl{T}'}$ is the supertype of $\gen{C}{\mathrm{dom}(\Delta_0)}$ with class $C'$.
The premise $\subtype{\emptyset}{\gen{C}{\mathrm{dom}(\Delta_0)}}{\gen{C'}{\pl{T}'}}$ of rule \textsc{castDown} uses the bounds $\emptyset$: a subtyping derivation between class types uses only rules \textsc{subRefl}, \textsc{subInherit} and \textsc{subInheritLocal}, which do not read $\Delta$.
Every type variable of $\mathrm{dom}(\Delta_0)$ occurs in $\pl{T}'$, thus the type arguments $\pl{T}_0$ of the source fix the type arguments $\pl{T}$ of the target.
Thus a value of type $\gen{C'}{\pl{T}_0}$ whose class is $C$ or a subclass of $C$ has type $\gen{C}{\pl{T}}$, and rule \textsc{ifThen} compares only class names.

\textsc{ifInstanceof} and \textsc{newLocal} work together to ensure type soundness: local classes are required to track dependencies on type parameters, and down-casts are consistency-checked to ensure that checking the class name only is sufficient to determine the generic instantiation.

Substitution of type variables (Figure \ref{fig:tysubst}) in our core language is not quite standard:
our substitution replaces every occurrence of a type variable, \emph{including} the ones in the method signatures of a local class.
Substitution does not rename the type variables it meets.
Substitution of type variables into expressions happens only during reduction, where the substituted types are ground.
Since the substituted types are ground, $\tsubst{\funnel{X_i}}{X_1,\ldots,X_n}{T_1,\ldots,T_n}=T_i$ is a ground type $G$, and the result is again a funnel.
In the domain of a substitution, bounds $\Delta$ stand for $\mathrm{dom}(\Delta)$.

Substitution of values in place of variables (Figure \ref{fig:valsubst}) is more standard.
A local class binds \Q@this@, as in Java: inside the methods of a local class, \Q@this@ is the local object, and the outer \Q@this@ is hidden.
Thus substitution of variables enters the methods of a local class for every variable except \Q@this@.
