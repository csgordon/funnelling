\section{More Failing Examples}
Example~1 is one of a family of programs that Java accepts with no warning and that fail at run time.
This section shows more programs of this family.

\subsection{Example 2: No Generic Supertype}
In Example~1, the local class \Q@MyFoo@ mentions \Q@X@ in its supertype \Q@Foo<X>@.
Example~2 exercises the same fault without needing a generic supertype.
Here \Q@MyFoo@ extends \Q@Object@, and \Q@X@ occurs only in the return type of the method \Q@x()@ of \Q@MyFoo@.
The method \Q@m@ returns \Q@Object@, so no type outside \Q@m@ mentions \Q@X@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 2
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(!(other instanceof MyFoo)){ return new MyFoo(); }
    MyFoo local= (MyFoo)other; // cast passes with no warnings (*\label{line:ex2cast}*)
    System.out.println("old one was "+f.apply(local.x())); //ClassCastException (*\label{line:ex2apply}*)
    return local;
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->""+i);
    Broken.<String>m(r1,"Hi",s->s);
  }
}
\end{lstlisting}
\end{minipage}

The first call of \Q@m@ instantiates \Q@X@ with \Q@Integer@, and returns a \Q@MyFoo@ whose method \Q@x()@ returns \Q@5@.
The second call of \Q@m@ instantiates \Q@X@ with \Q@String@.
In the second call, \Q@other instanceof MyFoo@ is true, and the cast \Q@(MyFoo)other@ at Line~\ref{line:ex2cast} succeeds with no warning.
Then \Q@local.x()@ has static type \Q@String@, but returns the \Q@Integer@ \Q@5@, and \Q@f.apply(local.x())@ at Line~\ref{line:ex2apply} throws a \Q@ClassCastException@.

No instruction of \Q@m@ performs the failing cast.
javac compiles the body of the lambda \Q@s->s@ into a private static method \Q@lambda$main$1(String)@ of the class \Q@Broken@.
At run time, the first evaluation of the lambda \Q@s->s@ calls \Q@LambdaMetafactory@, which generates a class implementing \Q@Function@; we call this class the \emph{lambda class}.
The method \Q@apply(Object)@ of the lambda class casts its argument to \Q@String@, and then calls \Q@lambda$main$1@ with the result of that cast.
Thus \Q@f.apply(local.x())@ passes the \Q@Integer@ \Q@5@ to the method \Q@apply@ of the lambda class, and the cast to \Q@String@ in that method throws the \Q@ClassCastException@.

The stack trace of the \Q@ClassCastException@ hides this.
\Q@LambdaMetafactory@ defines the lambda class as a hidden class, and the JVM omits the frames of the methods of hidden classes from stack traces, unless the JVM runs with the diagnostic option \Q@-XX:+ShowHiddenFrames@.
So the topmost frame of the stack trace is the frame of \Q@m@, at Line~\ref{line:ex2apply}.
The bytecode of \Q@m@ at Line~\ref{line:ex2apply} does contain a \Q@checkcast@ instruction to \Q@String@, on the result of \Q@f.apply@, but that instruction is never reached.
The failure is detected in the lambda class: in code that the programmer did not write, at a point that depends on how javac and the JVM implement lambdas.

\subsection{Example 3: No Explicit Cast}
Example~3 exercises the same fault without needing an explicit cast.
Java accepts Example~3 with no warning.
Here we rely on the \Q@other instanceof MyFoo local@ test to bind
\Q@local@ in one step.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 3
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(other instanceof MyFoo local){ // no cast, no warnings
      System.out.println("old one was "+f.apply(local.x())); //ClassCastException
    }
    return new MyFoo();
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->""+i);
    Broken.<String>m(r1,"Hi",s->s);
  }
}
\end{lstlisting}
\end{minipage}

As in Example~2, the method \Q@apply@ of the lambda class throws the \Q@ClassCastException@.

\subsection{Example 4: Pattern Matching in \texttt{switch}}
Example~4 exercises the same fault with a \Q@switch@ instead of an \Q@instanceof@.
Here the case \Q@case MyFoo local@ performs the same type test as the pattern \Q@other instanceof MyFoo local@ of Example~3.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 4
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    switch(other){
      case MyFoo local: // no cast, no warnings
        System.out.println("old one was "+f.apply(local.x())); //ClassCastException
        break;
      default:
        break;
    }
    return new MyFoo();
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->""+i);
    Broken.<String>m(r1,"Hi",s->s);
  }
}
\end{lstlisting}
\end{minipage}

\subsection{Example 5: No \texttt{checkcast} on the Result}
Example~5 exercises the same fault without a \Q@checkcast@ instruction on the result of \Q@f.apply@ in the bytecode of \Q@m@.
Example~5 could be expressed with either the \Q@switch@ of Example~4 or the \Q@instanceof@ of Example~3; here we chose the switch, but the other way would make the same point.
Example~5 uses \Q@Function<X,Integer>@ and the lambda \Q@s->s.length()@ instead of \Q@Function<X,String>@ and the lambda \Q@s->s@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 5
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,Integer> f){
    class MyFoo{ public X x(){ return x; } }
    switch(other){
      case MyFoo local: // no cast, no warnings
        System.out.println("old one was "+f.apply(local.x())); //ClassCastException
        break;
      default:
        break;
    }
    return new MyFoo();
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->i);
    Broken.<String>m(r1,"Hi",s->s.length());
  }
}
\end{lstlisting}
\end{minipage}

The failure is the failure of Example~2: the method \Q@apply@ of the lambda class casts its argument, the \Q@Integer@ \Q@5@, to \Q@String@ before calling \Q@lambda$main$1(String)@.
The difference is only in the bytecode of \Q@m@.
Here the result of \Q@f.apply@ has static type \Q@Integer@, and javac passes that result to the string concatenation without casting it to \Q@Integer@, since any object can be converted to a \Q@String@.
So the bytecode of \Q@m@ contains no \Q@checkcast@ instruction on the result of \Q@f.apply@.
In Examples~2 to~4, the bytecode of \Q@m@ contains a \Q@checkcast@ instruction to \Q@String@ on the result of \Q@f.apply@, but that instruction is never reached.

javac inserts a \Q@checkcast@ instruction where a value of an erased generic type is used at a more specific type.
In Example~1, such a \Q@checkcast@ instruction detects the failure: javac inserts it in \Q@main@, before the call of the overload \Q@println(String)@.
So one could expect a program with no \Q@checkcast@ instruction on the result of \Q@f.apply@ to fail later, in some virtual call, or not to fail at all.
Example~5 shows that this expectation is wrong.
In Examples~2 to~5, the value with the wrong type is the argument of \Q@f.apply@: \Q@local.x()@ has static type \Q@String@, but returns the \Q@Integer@ \Q@5@.
The method \Q@apply@ of the lambda class casts that argument to \Q@String@ before \Q@m@ receives any result from \Q@f.apply@.
Thus the failure is detected at the same point in Examples~2 to~5, whether or not the bytecode of \Q@m@ contains a \Q@checkcast@ instruction on the result of \Q@f.apply@.

\subsection{Example 6: \texttt{X} Only in Private Members}
Example~6 exercises the same fault without \Q@X@ in the public signature of \Q@MyFoo@.
Here \Q@MyFoo@ extends \Q@Object@, and its only public method \Q@show@ takes a \Q@MyFoo@ and returns a \Q@String@.
\Q@X@ occurs only in the type of the private field \Q@v@, and in the body of \Q@show@, through the captured \Q@f@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 6
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,String> f){
    class MyFoo{
      private final X v= x;
      public String show(MyFoo o){ return f.apply(o.v); }
    }
    MyFoo mine= new MyFoo();
    if(other instanceof MyFoo local){ // no cast, no warnings
      System.out.println("old one was "+mine.show(local)); //ClassCastException (*\label{line:ex6show}*)
    }
    return mine;
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->""+i);
    Broken.<String>m(r1,"Hi",s->s);
  }
}
\end{lstlisting}
\end{minipage}

The first call of \Q@m@ returns a \Q@MyFoo@ whose field \Q@v@ holds the \Q@Integer@ \Q@5@.
In the second call of \Q@m@, \Q@mine@ is a new \Q@MyFoo@ of the second call, and \Q@local@ is the \Q@MyFoo@ of the first call.
At Line~\ref{line:ex6show}, \Q@mine.show(local)@ applies the \Q@f@ of the second call, the lambda \Q@s->s@, to the field \Q@v@ of \Q@local@, the \Q@Integer@ \Q@5@.
As in Example~2, the method \Q@apply@ of the lambda class throws the \Q@ClassCastException@.
No type that a client of \Q@MyFoo@ can see mentions \Q@X@, and still the two instances of \Q@MyFoo@ disagree on \Q@X@.

\subsection{Example 7: Class Generics}
Example~7 moves Example~3 into a generic class:
\Q@X@ is a generic parameter of the class \Q@Box@ instead of a generic parameter of the method \Q@m@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 7
class Box<X> {
  final X x;
  Box(X x){ this.x= x; }
  Object m(Object other, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(other instanceof MyFoo local){ // error: Object cannot be safely cast to MyFoo (*\label{line:ex7test}*)
      System.out.println("old one was "+f.apply(local.x()));
    }
    return new MyFoo();
  }
}
public class Broken {
  public static void main(String[] a){
    Object r1= new Box<Integer>(5).m("anything",i->""+i);
    new Box<String>("Hi").m(r1,s->s);
  }
}
\end{lstlisting}
\end{minipage}

Example~7 marks the boundary of the family: with class generics, javac does flag the fault.
javac rejects Example~7 at Line~\ref{line:ex7test}, with the error \Q@Object cannot be safely cast to MyFoo@.
The method \Q@m@ is an instance method of \Q@Box<X>@, so \Q@MyFoo@ is an inner class of \Q@Box<X>@, with an enclosing instance of type \Q@Box<X>@.
javac types \Q@MyFoo@ as \Q@Box<X>.MyFoo@, as javac types a member class \Q@MyFoo@ of \Q@Box@.
So \Q@MyFoo@ is generic in \Q@X@, and \Q@other instanceof MyFoo@ is the uncheckable type test \Q@other instanceof Box<X>.MyFoo@.

The cast is flagged too.
The following method \Q@m@ replaces the method \Q@m@ of Example~7.
The type test against \Q@String@ replaces the type test against \Q@MyFoo@, which javac rejects, and the cast of Example~2 follows it.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 7 with a cast: the method m of Box
  Object m(Object other, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(other instanceof String){ return new MyFoo(); }
    MyFoo local= (MyFoo)other; // warning: [unchecked] unchecked cast (*\label{line:ex7cast}*)
    System.out.println("old one was "+f.apply(local.x())); //ClassCastException
    return local;
  }
\end{lstlisting}
\end{minipage}

javac accepts this program, but reports an unchecked warning for the cast at Line~\ref{line:ex7cast}.
At run time the cast succeeds, and the program fails as Example~2 fails.
So with class generics the program fails only after an unchecked warning, as a program with the cast \Q@(List<String>)o@ may fail.
In Examples~1 to~6 instead, javac reports nothing.

Thus for the generic parameters of the enclosing class, Java already exposes the captured generic types in the type of the local class,
through the type of its enclosing instance.
Java does not do the same for the generic parameters of the enclosing method: no type of the local class carries the instantiation of the generic parameters of a method.

\section{The Impact of Generic Reification}
\todo[inline]{Not yet verified: the claims on Roslyn lifted classes, Rust (E0401, closure and opaque type identity, precise capturing), Swift, D, OCaml and SML local exceptions, and Scala outer tests.}
A natural suspicion is that this problem is ``simply'' a consequence of generic erasure:
a language that cannot distinguish the generic instantiations of a class at run time must have difficulties of this sort.
There is some truth to this suspicion: javac accepts a cast that the JVM cannot check, because of erasure.
However, javac does flag uncheckable type tests:
for \Q@o@ of type \Q@Object@, javac reports an unchecked warning for the cast \Q@(List<String>)o@, and an error for \Q@o instanceof List<String>@.
javac reports nothing for Examples~1 to~6 because \Q@MyFoo@ is not generic:
the type test of \Q@other@ against \Q@MyFoo@ has no generic argument to leave unchecked.

Reification does not change this by itself.
A reified runtime can only check what the run-time identity of a class contains.
If the run-time identity of \Q@MyFoo@ is just the declared class \Q@MyFoo@, reification adds nothing to the cast \Q@(MyFoo)other@.
Java treats the class \Q@MyFoo extends Foo<X>@ as it treats the class \Q@String extends Comparable<String>@: a cast inspects only the declared class.
A cast to \Q@String@ does not inspect the generic argument of \Q@Comparable<String>@,
and a cast to \Q@MyFoo@ does not inspect the generic argument of \Q@Foo<X>@.
But the argument \Q@String@ of \Q@Comparable<String>@ is a constant of the class \Q@String@: a reified runtime records it once, in the class table of \Q@String@.
The argument \Q@X@ of \Q@Foo<X>@ is not a constant of the class \Q@MyFoo@: \Q@X@ is free in the declaration of \Q@MyFoo@, and \Q@X@ changes between calls of \Q@m@.

The implementations of method-local classes, and of the similar features of other languages, differ in the granularity of the identity of the local class.
The identity of the local class matters in two places:
in the type system, where it decides whether two types of the local class are the same type,
and at run time, where it decides the result of casts and type tests.
There are three granularities: (1) one identity per declared class, (2) one identity per instantiation of the enclosing scope, and (3) one identity per evaluation of the declaration.%
\footnote{Some languages avoid the choice by forbidding the capture of generic types.
In Rust, a struct, function or impl declared inside a generic function can not use the generic parameters of the enclosing function (error E0401):
the programmer must declare those generic parameters again on the inner item.
Swift rejects a type declared inside a generic function.
\todo[inline]{cite Swift: type cannot be nested in generic function}}

In (1), the declaration of a local class is a single point in the source code.
So the local class \Q@MyFoo@ is one class, and the identity of \Q@MyFoo@ is its declaration point, the same for every instantiation of \Q@m@.
In (2), generic classes and generic methods are functions from generic arguments to concrete classes and methods:
\Q@static <X> Object m(..)@ declares infinitely many methods \Q@m<Integer>@, \Q@m<String>@, and so on, one for each instantiation of \Q@X@.
In the same way, the generic class declaration \Q@class Foo<X>@ declares infinitely many classes \Q@Foo<Integer>@, \Q@Foo<String>@, and so on.
So in (2) each method \Q@m<T>@ declares its own local class \Q@MyFoo@, since the body of each \Q@m<T>@ is the body of a different method.

Java checks casts and type tests with granularity (1):
each class has a declaration point, and for each declaration point there is one \Q@Class<?>@ object, whose identity decides the result of the casts that the JVM checks.
For class generics, the Java type system instead assumes granularity (2), as Example~7 shows.
For member classes, the Java Language Specification states this granularity directly:
if a generic class \Q@C@ has a non-generic member class \Q@D@, then \Q@C<String>.D@ is a parameterized type, even though \Q@D@ is not generic~\cite[\S 4.5]{jls}.
A local class declared in an instance method is an inner class of the enclosing class~\cite[\S 8.1.3]{jls}, and javac gives the local class the same kind of type:
in Example~7, \Q@MyFoo@ is \Q@Box<X>.MyFoo@, so \Q@Box<String>.MyFoo@ and \Q@Box<Integer>.MyFoo@ are different types.
A narrowing conversion from \Q@Object@ to such a parameterized type is unchecked~\cite[\S 5.1.6.2]{jls}:
the cast \Q@(MyFoo)other@ causes an unchecked warning, and the type test \Q@other instanceof MyFoo@ is a compile-time error~\cite[\S 15.20.2]{jls}.
These are the warning and the error of Example~7.
However, generic methods are not treated in the same way:
in Examples~1 to~6, the type of the local class is \Q@MyFoo@, not \Q@m<X>.MyFoo@.
For method generics, the Java type system assumes granularity (1), as the casts do, so javac reports nothing and the program fails at run time.
If the type of a local class contained the enclosing method and its generic instantiation, as in \Q@Box<T1>.m<T2>.MyFoo@,
then javac would flag the problem for generic methods too, as it does for generic classes.

A version of Java with reified generics could solve the mismatch in Example~7, between the granularity (1) of the casts and the granularity (2) of the types.
But reification would not change Examples~1 to~6, unless the types of local classes take the form \Q@A<T1>.m<T2>.MyFoo@.
Moreover, Example~6 shows that the generic types needed by a local class can stay fully private:
in Example~6, \Q@X@ occurs only in the private field \Q@v@ and in the body of \Q@show@.
Without an explicit way to put the needed generic types in the public API of the local class, such generic types stay private details.
A type error caused by a fully private detail would make type checking non-modular.
A failing dynamic cast caused by a fully private detail would make the private detail observable, and the language overall less predictable.

Granularity (2) is the default view for languages that implement parametric polymorphism by generative programming instead of generic programming~\tocite{generative programming}%
\footnote{Also called templating or heterogeneous compilation.},
like C++ or early experiments with generic Java~\cite{agesen1997adding}.
There each instantiation of \Q@m@ with different generic parameters is compiled separately, resulting in separate class declarations for each instantiation:
generative programming forces (2) as the interpretation both at compile time and at run time.
Each instantiation of \Q@m@ is a separate method of the compiled program, with its own local class \Q@MyFoo@.
Consider reinterpreting Example~1 in C++.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em,language=c++]
// Example 1 in C++
class Object{ public: virtual ~Object(){} };
template<typename X> class Foo : public Object {
    public: virtual X x() { return x(); } };
template<typename X>
Foo<X>* m(Object* other, const X* x) {
    class MyFoo : public Foo<X> {
        const X* v;
      public: MyFoo(const X* v):v(v){} X x() { return *v; } };
    MyFoo* d = dynamic_cast<MyFoo*>(other);(*\label{line:cpp_cast}*)
    if(d == nullptr) { return new MyFoo(x); }
    return d;
}
\end{lstlisting}
\end{minipage}

A C++ local class cannot use the parameters of its enclosing function, so \Q@MyFoo@ receives \Q@x@ through its constructor.
\Q@Object@ has a virtual destructor, since \Q@dynamic_cast@ requires a polymorphic source type.
The calls \Q@r1=m<int>(nullptr,&i)@ and then \Q@m<std::string>(r1,&s)@ mirror Example~1.
In the second call, the \Q@dynamic_cast@ at Line \ref{line:cpp_cast} returns \Q@nullptr@:
\Q@m<int>@ and \Q@m<std::string>@ declare two distinct classes \Q@MyFoo@, and \Q@r1@ is an instance of the first one.
Thus the second call returns a new \Q@MyFoo@, as a sound type test should.
In its diagnostics, \texttt{gcc} names the first class \Q@m<int>(Object*, const int*)::MyFoo@:
the instantiation of the method signature is the scope of the declaration of \Q@MyFoo@.
Inside the template \Q@m<X>@, the C++ type system sees \Q@MyFoo@ as the dependent type \Q@m<X>::MyFoo@.
So C++ does expose \Q@X@ in the type of \Q@MyFoo@: through the name of the enclosing scope instead of through a generic parameter of \Q@MyFoo@.
This is the form \Q@m<T2>.MyFoo@ that the Java type system does not have.
D works in the same way, and its ``Voldemort types'' make the scope visible:
a local struct \Q@S@ returned from the template function \Q@f@ has the type \Q@f!int.S@ when \Q@f@ is instantiated with \Q@int@~\tocite{D Voldemort types}.

C\# has no local classes, but its compiler lifts closures, local functions, iterators and async methods into generated classes.
Inside a generic method \Q@M<T>@, the generated classes are themselves generic in the captured \Q@T@, as in \Q@<>c__DisplayClass0_0<T>@~\tocite{Roslyn lowering}.
Since .NET reifies generics, the generated classes for \Q@M<int>@ and \Q@M<string>@ can be observed as distinct at run-time.
A programmer can not name these generated classes in C\# source, so a programmer can not write a cast to them.

Rust closures and \Q@impl Trait@ opaque types capture the generic parameters of the enclosing function,
and the type of the closure, or the opaque type, includes those generic parameters in its identity:
the \Q@TypeId@ of a closure created in \Q@m::<i32>@ differs from the \Q@TypeId@ of the same closure created in \Q@m::<String>@~\cite{rustClosures}.
The precise capturing syntax of Rust 2024, \Q@impl Trait + use<T>@, lists explicitly the generic parameters that an opaque type captures~\tocite{Rust precise capturing RFC 3617}.

Generative programming has subtle costs and wide-ranging consequences for language design, not just implementation,
and complex performance consequences~\cite{odersky2001two,kennedy2001design}.
However, these costs are not intrinsic to granularity (2):
.NET keeps a single implementation for the instantiations at reference types and still gives each instantiation its own run-time identity~\cite{kennedy2001design}.

Each of these sound designs follows granularity (2), and makes the captured generic types part of the identity of the local class:
in the type system and at run time (C++, D, Rust), or only at run time (C\# generated classes).

Overall, reification simply changes when a cast can be accepted by the type system.
With reification we can have more expressive run time checks, so a more relaxed type system can still be sound.

Granularity (3) is a more extreme version of granularity (2): each evaluation of a declaration creates a new class, even for the same instantiation of the generic parameters.
In OCaml, \Q@let exception E of a in ...@ creates a fresh exception constructor each time the declaration is evaluated;
local exception declarations in Standard ML are generative in the same way~\tocite{OCaml local exceptions, SML generative exceptions}.
A handler for \Q@E@ does not catch an \Q@E@ raised by another evaluation of the declaration, whatever the instantiation of \Q@a@.
Scala has granularity (3) for captured values instead of captured types.
An instance of an inner class \Q@Inner@ captures its enclosing instance \Q@$outer@, and its type is the path-dependent type \Q@a.Inner@.
For the pattern \Q@case i: a.Inner@, the Scala compiler emits an ``outer test'' that compares the captured \Q@$outer@ with \Q@a@~\tocite{Scala outer tests}.
Even here the type system exposes what is captured: inside the class of \Q@a@, \Q@Inner@ means \Q@this.Inner@.
Granularity (3) is sound, but it is stricter than needed to avoid the problem at hand.

\section{Funnelling}
Granularities (1), (2) and (3) are points in a space of design options,
but other points lie between them.
Funnelling, the approach we present in this paper, lies between (1) and (2):
in Example~1, \Q@MyFoo@ funnels \Q@X@ and becomes \Q@MyFoo<X>@.
For \Q@other@ of type \Q@Object@, the existing rules of Java then flag \Q@other instanceof MyFoo<X>@ with an error and \Q@(MyFoo<X>)other@ with an unchecked warning, because \Q@Object@ does not determine \Q@X@.
These are the two compile-time points of the introduction.
With reification, the same type test would be accepted by the compiler, and it would return false in the second call of \Q@m@.

We now show funnelling on the core language of Section~\ref{sec:core}, a version of Featherweight Java~\cite{fj} rich enough to express the problem.
The core language has generics, type tests and local classes.
A local class is written as an expression, like an anonymous class in Java, but with a name:
\Q@new MyFoo<Fs> extends Foo<Ts>(es){Ms}@ declares the local class \Q@MyFoo@ and creates an instance of it.
This brings method-local classes into an expression-based calculus, without modelling statements.
The funnels \Q@Fs@ are the generic parameters of \Q@MyFoo@: a funnel \Q@X funnel@ funnels the type variable \Q@X@ in scope.
During reduction, \Q@X funnel@ becomes the ground type that instantiates \Q@X@.
The type test \Q@if (e instanceof T x){ e1 } else { e2 }@ binds \Q@x@ in \Q@e1@; the core language has no casts.
In the listings, we omit the empty \Q@<>@ of methods and calls, and we write \Q@<X>@ for \Q@<X extends Object<>>@.
This is Example~1 in the core language, without funnels:

\begin{lstlisting}
class A<> extends Object<>{}
class B<> extends Object<>{ B<> onlyB(){ return new B<>(); } }
class Foo<X> extends Object<>{ X x(){ return this.x(); } }
