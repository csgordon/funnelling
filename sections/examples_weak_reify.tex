\section{More Failing Examples}
Example~1 is one of a family of programs that Java accepts with no warning and that fail at run time.
This section shows more programs of this family.

\subsection{Example 2: No Generic Supertype}
In Example~1, the local class \Q@MyFoo@ mentions \Q@X@ in its supertype \Q@Foo<X>@.
Example~2 exercises the same fault without needing a generic supertype.
Here \Q@MyFoo@ extends \Q@Object@, and \Q@X@ occurs only in the return type of the method \Q@x()@ of \Q@MyFoo@.
The method \Q@m@ returns \Q@Object@, so no type outside \Q@m@ mentions \Q@X@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 2
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(!(other instanceof MyFoo)){ return new MyFoo(); }
    MyFoo local= (MyFoo)other; // cast passes with no warnings (*\label{line:ex2cast}*)
    System.out.println("old was "+f.apply(local.x())); //ClassCastException (*\label{line:ex2apply}*)
    return local;
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->""+i);
    Broken.<String>m(r1,"Hi",s->s);
  }
}
\end{lstlisting}
\end{minipage}

The first call of \Q@m@ instantiates \Q@X@ with \Q@Integer@, and returns a \Q@MyFoo@ whose method \Q@x()@ returns \Q@5@.
The second call of \Q@m@ instantiates \Q@X@ with \Q@String@.
In the second call, \Q@other instanceof MyFoo@ is true, and the cast \Q@(MyFoo)other@ at Line~\ref{line:ex2cast} succeeds with no warning.
Then \Q@local.x()@ has static type \Q@String@, but returns the \Q@Integer@ \Q@5@, and \Q@f.apply(local.x())@ at Line~\ref{line:ex2apply} throws a \Q@ClassCastException@.

\todo[inline]{consider moving this level of detail (the cast is in a generated synthetic method) to the appendix. Maybe just say "the cast is in generated code" and put the rest in an appendix? Or footnote?}
No instruction of \Q@m@ performs the failing cast.
\texttt{javac} compiles the body of the lambda \Q@s->s@ into a private static method \Q@lambda$main$1(String)@ of the class \Q@Broken@.
At run time, the first evaluation of the lambda \Q@s->s@ calls \Q@LambdaMetafactory@, which generates a class implementing \Q@Function@; we call this class the \emph{lambda class}.
The method \Q@apply(Object)@ of the lambda class casts its argument to \Q@String@, and then calls \Q@lambda$main$1@ with the result of that cast.
Thus \Q@f.apply(local.x())@ passes the \Q@Integer@ \Q@5@ to the method \Q@apply@ of the lambda class, and the cast to \Q@String@ in that method throws the \Q@ClassCastException@.

The stack trace of the \Q@ClassCastException@ hides this.
\Q@LambdaMetafactory@ defines the lambda class as a hidden class, and the JVM omits the frames of the methods of hidden classes from stack traces, unless the JVM runs with the diagnostic option \Q@-XX:+ShowHiddenFrames@.
So the topmost frame of the stack trace is the frame of \Q@m@, at Line~\ref{line:ex2apply}.
The bytecode of \Q@m@ at Line~\ref{line:ex2apply} does contain a \Q@checkcast@ instruction to \Q@String@, on the result of \Q@f.apply@, but that instruction is never reached.
The failure is detected in the lambda class: in code that the programmer did not write, at a point that depends on how javac and the JVM implement lambdas.

\subsection{Example 3: No Explicit Cast}
Example~3 exercises the same fault without needing an explicit cast.
Java accepts Example~3 with no warning.
Here we rely on the \Q@other instanceof MyFoo local@ test to bind
\Q@local@ in one step.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 3
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(other instanceof MyFoo local){ // no cast, no warnings
      System.out.println("old was "+f.apply(local.x())); //ClassCastException
    }
    return new MyFoo();
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->""+i);
    Broken.<String>m(r1,"Hi",s->s);
  }
}
\end{lstlisting}
\end{minipage}

As in Example~2, the method \Q@apply@ of the lambda class throws the \Q@ClassCastException@.

\subsection{Example 5: No \Q@checkcast@ on the Result}

Example~5 exercises the same fault without a \Q@checkcast@ instruction on the result of \Q@f.apply@ in the bytecode of \Q@m@.
Example~5 could be expressed with either the \Q@switch@ of Example~4 or the \Q@instanceof@ of Example~3; here we chose the switch, but the other way would make the same point.
Example~5 uses \Q@Function<X,Integer>@ and the lambda \Q@s->s.length()@ instead of \Q@Function<X,String>@ and the lambda \Q@s->s@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Example 5
public class Broken {
  static <X> Object m(Object other, final X x, Function<X,Integer> f){
    class MyFoo{ public X x(){ return x; } }
    switch(other){
      case MyFoo local: // no cast, no warnings
        System.out.println("old was "+f.apply(local.x())); //ClassCastException
        break;
      default:
        break;
    }
    return new MyFoo();
  }
  public static void main(String[] a) {
    Object r1= Broken.<Integer>m("anything",5,i->i);
    Broken.<String>m(r1,"Hi",s->s.length());
  }
}
\end{lstlisting}
\end{minipage}

The failure is the failure of Example~2: the method \Q@apply@ of the lambda class casts its argument, the \Q@Integer@ \Q@5@, to \Q@String@ before calling \Q@lambda$main$1(String)@.
The difference is only in the bytecode of \Q@m@.
Here the result of \Q@f.apply@ has static type \Q@Integer@, and javac passes that result to the string concatenation without casting it to \Q@Integer@, since any object can be converted to a \Q@String@.
So the bytecode of \Q@m@ contains no \Q@checkcast@ instruction on the result of \Q@f.apply@.
In Examples~2 to~4, the bytecode of \Q@m@ contains a \Q@checkcast@ instruction to \Q@String@ on the result of \Q@f.apply@, but that instruction is never reached.

javac inserts a \Q@checkcast@ instruction where a value of an erased generic type is used at a more specific type.
In Example~1, such a \Q@checkcast@ instruction detects the failure: javac inserts it in \Q@main@, before the call of the overload \Q@println(String)@.
So one could expect a program with no \Q@checkcast@ instruction on the result of \Q@f.apply@ to fail later, in some virtual call, or not to fail at all.
Example~5 shows that this expectation is wrong.
In Examples~2 to~5, the value with the wrong type is the argument of \Q@f.apply@: \Q@local.x()@ has static type \Q@String@, but returns the \Q@Integer@ \Q@5@.
The method \Q@apply@ of the lambda class casts that argument to \Q@String@ before \Q@m@ receives any result from \Q@f.apply@.
Thus the failure is detected at the same point in Examples~2 to~5, whether or not the bytecode of \Q@m@ contains a \Q@checkcast@ instruction on the result of \Q@f.apply@.

Example~6 exercises the same fault without \Q@X@ in the public signature of \Q@MyFoo@.
Here \Q@MyFoo@ extends \Q@Object@, and its only public method \Q@show@ takes a \Q@MyFoo@ and returns a \Q@String@.
\Q@X@ occurs only in the type of the private field \Q@v@, and in the body of \Q@show@, through the captured \Q@f@.

The first call of \Q@m@ returns a \Q@MyFoo@ whose field \Q@v@ holds the \Q@Integer@ \Q@5@.
In the second call of \Q@m@, \Q@mine@ is a new \Q@MyFoo@ of the second call, and \Q@local@ is the \Q@MyFoo@ of the first call.
At Line~\ref{line:ex6show}, \Q@mine.show(local)@ applies the \Q@f@ of the second call, the lambda \Q@s->s@, to the field \Q@v@ of \Q@local@, the \Q@Integer@ \Q@5@.

\subsection{Counterexample 7: Class Generics}
Counterexample~7 moves Example~3 into a generic class:
\Q@X@ is a generic parameter of the class \Q@Box@ instead of a generic parameter of the method \Q@m@.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Counterexample 7
class Box<X> {
  final X x;
  Box(X x){ this.x= x; }
  Object m(Object other, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(other instanceof MyFoo local){ // error: Object cannot be safely cast to MyFoo (*\label{line:ex7test}*)
      System.out.println("old was "+f.apply(local.x()));
    }
    return new MyFoo();
  }
}
public class Broken {
  public static void main(String[] a){
    Object r1= new Box<Integer>(5).m("anything",i->""+i);
    new Box<String>("Hi").m(r1,s->s);
  }
}
\end{lstlisting}
\end{minipage}

Counterexample~7 marks the boundary of the family: with class generics, javac does flag the fault.
javac rejects Counterexample~7 at Line~\ref{line:ex7test}, with the error \Q@Object cannot be safely cast to MyFoo@.
The method \Q@m@ is an instance method of \Q@Box<X>@, so \Q@MyFoo@ is an inner class of \Q@Box<X>@, with an enclosing instance of type \Q@Box<X>@.
javac types \Q@MyFoo@ as \Q@Box<X>.MyFoo@, as javac types a member class \Q@MyFoo@ of \Q@Box@.
So \Q@MyFoo@ is generic in \Q@X@, and \Q@other instanceof MyFoo@ is the uncheckable type test \Q@other instanceof Box<X>.MyFoo@.

The cast is flagged too.
The following method \Q@m@ replaces the method \Q@m@ of Counterexample~7.
The type test against \Q@String@ replaces the type test against \Q@MyFoo@, which javac rejects, and the cast of Example~2 follows it.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[numbers=left,xleftmargin=2em]
// Counterexample 7 with a cast: the method m of Box
  Object m(Object other, Function<X,String> f){
    class MyFoo{ public X x(){ return x; } }
    if(other instanceof String){ return new MyFoo(); }
    MyFoo local= (MyFoo)other; // warning: [unchecked] unchecked cast (*\label{line:ex7cast}*)
    System.out.println("old was "+f.apply(local.x())); //ClassCastException
    return local;
  }
\end{lstlisting}
\end{minipage}

javac accepts this program, but reports an unchecked warning for the cast at Line~\ref{line:ex7cast}.
At run time the cast succeeds, and the program fails as Example~2 fails.
So with class generics the program fails only after an unchecked warning, as a program with the cast \Q@(List<String>)o@ may fail.
In Examples~1 to~6 instead, javac reports nothing.

Thus for the generic parameters of the enclosing class, Java already exposes the captured generic types in the type of the local class,
through the type of its enclosing instance.
Java does not do the same for the generic parameters of the enclosing method: no type of the local class carries the instantiation of the generic parameters of a method.


\section{Funnelling}
\label{sec:funnelling}

A natural suspicion is that this problem is ``simply'' a consequence of generic erasure:
a language that cannot distinguish the generic instantiations of a class at run time must have difficulties of this sort.
There is some truth to this suspicion: javac can accept a cast that the JVM cannot check, because of erasure.
However, javac does flag uncheckable type tests:
for \Q@o@ of type \Q@Object@, javac reports an unchecked warning for the cast \Q@(List<String>)o@, and an error for \Q@o instanceof List<String>@.
javac reports nothing for Examples~1 to~6 because \Q@MyFoo@ is not generic:
the type test of \Q@other@ against \Q@MyFoo@ has no generic argument to leave unchecked.
So reification does not change the situation by itself.\todo{this paragraph may duplicate counterexample 7 text, otherwise we should move it there}

The implementations of method-local classes, and of the similar features of other languages, differ in the granularity of the identity of the local class.
The identity of the local class matters in two places:
in the type system, where it decides whether two types of the local class are the same type,
and at run time, where it decides the result of casts and type tests.
There are three granularities:
\begin{enumerate}
\item \textbf{Identity as Declaration Point}: The declaration of a local class is a single point in the source code.
So the local class \Q@MyFoo@ is one class, and the identity of \Q@MyFoo@ is its declaration point, the same for every instantiation of \Q@m@.
\item \textbf{Identity as Generic Instantiation}:
Generic classes and generic methods are functions from generic arguments to concrete classes and methods:
\Q@static <X> Object m(..)@ declares infinitely many methods \Q@m<Integer>@, \Q@m<String>@, and so on, one for each instantiation of \Q@X@.
In the same way, the generic class declaration \Q@class Foo<X>@ declares infinitely many classes \Q@Foo<Integer>@, \Q@Foo<String>@, and so on.
So each method \Q@m<T>@ declares its own local class \Q@MyFoo@, since the body of each \Q@m<T>@ is the body of a different method.
\item \textbf{Identity as Dynamic Evaluation}: 
A declaration creates a new class, even for the same instantiation of the generic parameters.
Scala has this granularity for captured values instead of captured types.
An instance of an inner class \Q@Inner@ captures its enclosing instance \Q@$outer@, and its type is the path-dependent type \Q@a.Inner@.
For the pattern \Q@case i: a.Inner@, the Scala compiler emits an ``outer test'' that compares the captured \Q@$outer@ with \Q@a@~\tocite{Scala outer tests}.%
\footnote{Even here the type system exposes what is captured: inside the class of \Q@a@, \Q@Inner@ means \Q@this.Inner@.}
This is sound, but it is stricter than needed to avoid the problem at hand.
\end{enumerate}

For method generics, the Java type system assumes granularity (1), as the casts do, so javac reports nothing and the program fails at run time.
If the type of a local class contained the enclosing method and its generic instantiation, as in \Q@Box<T1>.m<T2>.MyFoo@,
then javac would flag the problem for generic methods too, as it does for generic classes.
A version of Java with reified generics could solve the mismatch in Counterexample~7, between the granularity (1) of the casts and the granularity (2) of the types.
But reification would not change Examples~1 to~6, unless the types of local classes take the form \Q@A<T1>.m<T2>.MyFoo@.

Granularities (1), (2) and (3) are points in a space of design options,
but other points lie between them.
Funnelling, the approach we present in this paper, lies between (1) and (2):
in Example~1, \Q@MyFoo@ funnels \Q@X@ and becomes \Q@MyFoo<X>@.
For \Q@other@ of type \Q@Object@, the existing rules of Java then flag \Q@other instanceof MyFoo<X>@ with an error and \Q@(MyFoo<X>)other@ with an unchecked warning, because \Q@Object@ does not determine \Q@X@.
These are the two compile-time points of the introduction.
With reification, the same type test would be accepted by the compiler, and it would return false in the second call of \Q@m@.

We now show funnelling on the core language of Section~\ref{sec:core}, a version of Featherweight Java~\cite{fj} rich enough to express the problem.
The core language has generics, type tests and local classes.
A local class is written as an expression, like an anonymous class in Java, but with a name:
\Q@new MyFoo<Fs> extends Foo<Ts>(es){Ms}@ declares the local class \Q@MyFoo@ and creates an instance of it.
This brings method-local classes into an expression-based calculus, without modelling statements.
The funnels \Q@Fs@ are the generic parameters of \Q@MyFoo@: a funnel \Q@X funnel@ funnels the type variable \Q@X@ in scope.
During reduction, \Q@X funnel@ becomes the ground type that instantiates \Q@X@.
The type test \Q@if (e instanceof T x){ e1 } else { e2 }@ binds \Q@x@ in \Q@e1@; the core language has no cast expression.
In the listings, we omit the empty \Q@<>@ of methods and calls, and we write \Q@<X>@ for \Q@<X extends Object<>>@.
This is Example~1 in the core language, without funnels:

\begin{lstlisting}
class A<> extends Object<>{}
class B<> extends Object<>{ B<> onlyB(){ return new B<>(); } }
class Foo<X> extends Object<>{ X x(){ return this.x(); } }
class Broken<> extends Object<>{
  <X> Foo<X> m(Object<> other, X x){ return
    if (other instanceof MyFoo<> w){ w }
    else { new MyFoo<> extends Foo<X>(){ X x(){ return x; } } }; }
}
\end{lstlisting}

As in Java, the type of the local class is \Q@MyFoo<>@, with no generic parameters.
Section~\ref{sec:core} presents the type rules and the small step reduction of the core language.
The type rules of Section~\ref{sec:core} encode funnelling.
With those type rules, the example above is ill typed: the supertype \Q@Foo<X>@ of \Q@MyFoo@ mentions \Q@X@, but \Q@MyFoo@ does not funnel \Q@X@.
Rule \textsc{new-local-java} enables the unsound Java typing:
\begin{mathpar}
\inferrule[new-local-java]{
  \kind{\Delta}{\gen{C'}{\pl{T}}}\\
  \typing{\Delta}{\Gamma}{\obj{C'}{\pl{T}}{\pl{e}}}{\_}\\\\
  \mok{\Delta}{\Gamma\setminus\this,\gen{C}{}\gap\this}{\pl{M}}\\\\
  \mathsf{overrideOk}(\Delta,\gen{C'}{\pl{T}},\pl{M})
}{
  \typing{\Delta}{\Gamma}{
    \innerobj{C}{}{C'}{\pl{T}}{\pl{e}}{\pl{M}}
  }{\gen{C}{}}
}
\end{mathpar}
Rule \textsc{new-local-java} uses the syntax \Q@new C<> extends C'<Ts>(es){Ms}@.
This syntax is an intermediate form between method-local classes and anonymous classes of Java.
A method-local class \Q@class C<> extends C'<Ts>{ C(){ super(es); } Ms }@ is declared first, and then instantiated with \Q@new C<>()@.
An anonymous class \Q@new C'<Ts>(es){Ms}@ is declared and instantiated by a single expression.
The syntax \Q@new C<> extends C'<Ts>(es){Ms}@ forms a (named) local class.
A local class creates an instance as an anonymous class does, thus a local class is easy to use in an expression-based language.
A local class also declares its own name, thus \Q@instanceof@ can test for a local class.
\\[1ex]
Rule \textsc{new-local-java} types the methods $\pl{M}$ of the local class $C$ under all the bounds $\Delta$ and all the variables $\Gamma$ in scope, except \Q@this@, which has type $\gen{C}{}$.
The example above is well typed using the type rules of Section~\ref{sec:core} and rule \textsc{new-local-java}.
The main expression is the first line of the reduction below, and it has type \Q@B<>@.
We now show the small step reduction using the abbreviations \Q@eA@, \Q@vA@ and \Q@vB@, and omitting the renaming of bound variables:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
eA = new Broken<>().<A<>>m(new Foo<A<>>(), new A<>())
vA = new MyFoo<> extends Foo<A<>>(){ A<> x(){ return new A<>(); } }
vB = new MyFoo<> extends Foo<B<>>(){ B<> x(){ return new B<>(); } }

    new Broken<>().<B<>>m(eA, new B<>()).x().onlyB()
(*$\rightarrow^{\ast}$*) new Broken<>().<B<>>m(vA, new B<>()).x().onlyB()
(*$\rightarrow^{\ast}$*) (if (vA instanceof MyFoo<> w){ w } else { vB }).x().onlyB()
(*$\rightarrow$*)  vA.x().onlyB()
(*$\rightarrow$*)  new A<>().onlyB()
\end{lstlisting}
\end{minipage}

The first call of \Q@m@ reduces \Q@eA@ to \Q@vA@ with rules \textsc{simpleAddSuper}, \textsc{simpleFound} and \textsc{ifElse}.
The type of \Q@vA@ is \Q@MyFoo<>@: the instantiation \Q@A<>@ of \Q@X@ shows only in the supertype \Q@Foo<A<>>@ and in the method \Q@x@.
In the second call of \Q@m@, rule \textsc{ifThen} checks only that the class of \Q@vA@ is a subclass of \Q@MyFoo@.
Thus the second call returns \Q@vA@, a \Q@Foo<A<>>@, as a \Q@Foo<B<>>@.
The last expression calls \Q@onlyB@ on an \Q@A<>@, and \Q@A<>@ does not have a method called \Q@onlyB@.
Rule \textsc{searchSuper} looks for \Q@onlyB@ up to \Q@Object<>@, where no rule applies: the reduction is stuck.

With funnelling, \Q@MyFoo@ must funnel \Q@X@, written \Q@new MyFoo<X funnel>@,
and instances of the local class are of type \Q@MyFoo<X>@.
Rule \textsc{cast-down} accepts a type test only when the static type determines \Q@X@, as Java does.
Thus \Q@other instanceof MyFoo<X> w@ is ill typed for \Q@Object<> other@, and the method \Q@m@ is ill typed.
This is the rule by which Java rejects \Q@o instanceof List<String>@ for \Q@Object o@.
If we change the signature of \Q@m@ as follows, the method \Q@m@ is well typed:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
  <X> Foo<X> m(Foo<X> other, X x){ return
    if (other instanceof MyFoo<X> w){ w }
    else { new MyFoo<X funnel> extends Foo<X>(){ X x(){ return x; } } }; }
\end{lstlisting}
\end{minipage}

Now \Q@eA@ is a well typed expression of type \Q@Foo<A<>>@, but the main expression is ill typed:
the second call of \Q@m@ expects a \Q@Foo<B<>>@ as the first argument, but \Q@eA@ is a \Q@Foo<A<>>@.

With reification, the funnelled method \Q@m@ with \Q@Object<> other@ would be well typed, but the reduction would change.
In the second call of \Q@m@, the type test of the \Q@MyFoo<A<>>@ created by the first call against \Q@MyFoo<B<>>@ is false.
The second call returns a new \Q@MyFoo<B<>>@, and the main expression reduces to \Q@new B<>()@.
Reification without funnelling does not help:
if we allow the value \Q@vA@ to have type \Q@MyFoo<>@, even a reified type test of \Q@vA@ against \Q@MyFoo<>@ is true.
